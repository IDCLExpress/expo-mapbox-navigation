# SAFEROUTE-283 — Protocol 1: a route change must release the previous route's resources

## Owner requirement (verbatim, drives this design)

> "These processes are all processing. And even though you're muting the output, you're
> still processing each of the processes. It doesn't happen in the beginning, but after
> a while you keep hitting buttons, it ties up all the memory and it locks everything
> up. That's exactly what's happening. We're freezing up the app. As soon as somebody
> hits a button, all those processes need to be canceled and released, everything
> released, so that this new process can work effectively."

The requirement is teardown, not suppression. Muting an output while its producer keeps
running does not satisfy this. Cancelled work must also be RELEASED.

## Defect 1 — camera observer registered per route change, never released

`navigationCamera.registerNavigationCameraStateChangeObserver { ... }` is at L483,
INSIDE `routesObserver.onRoutesChanged`. It therefore runs on every route change.

No `unregisterNavigationCameraStateChangeObserver` exists anywhere in the file. The
teardown at L936-941 covers only the six `mapboxNavigation` observers.

Consequences, in order of severity:
1. Every camera state transition invokes N observers, where N is the number of route
   changes so far. Per-event work grows without bound. This matches the reported
   symptom precisely: fine at first, degrading as the user presses the button.
2. Each lambda captures `recenterButton`, holding a View and therefore its Context.

## Defect 2 — TextToSpeech engines created per route change, never shut down

7 created, 7 bound, 0 shut down across 6 route changes. Each holds a live service
connection to `com.google.android.tts`. Reviewers should establish WHERE these are
constructed — SafeRoute's own code constructs only `ttsWarmup` (in
ExpoMapboxNavigationModule.kt, which does call shutdown()), so the per-route instances
are most likely created inside `MapboxVoiceInstructionsPlayer`'s fallback path, which
every SafeRoute announcement reaches because fabricated `VoiceInstructions` always
fail cloud synthesis (item 42). Confirm against the SDK rather than assume.

## Defect 3 — mute does not stop the pipeline

`isMuted` appears at L115, L183, L186, L188, L1094-1098, L1232 — every occurrence sets
a volume or a button icon. No speech path consults it. `enqueueSpeech`, `speakText`,
`speechCallback` and `onSpeechFinished` do not check it.

So while muted, an announcement still: synthesises, occupies `speechInFlight` (blocking
the queue for its full duration), and calls `voiceInstructionsPlayer.play()` — which
still requests and abandons system audio focus. Audio focus is a system-wide claim
unaffected by player volume, so a muted announcement still interrupts other audio,
including the driver's own music and the other in-app voice.

Owner has observed this behaviour previously in other contexts.

## Relationship to SAFEROUTE-282

282 (P1 APPROVED 487f71df, P2 CONDITIONAL e0a74a22) fixes the speech QUEUE stalling
after `speechApi.cancel()`. It is the same failure class as the above: the route-change
path cancels or suppresses work without releasing it. 282's P2 conditions included
"guard against double registration of observers", which overlaps Defect 1.

Reviewers should state whether 283 should absorb 282 or build on it. Implementing the
same function twice is the risk to avoid.

## What the design must satisfy

1. A route change releases every resource held for the previous route — observers,
   engines, queued work, in-flight synthesis.
2. Release is idempotent and safe when nothing is held.
3. Registration that must happen once must not live inside a per-route callback.
4. Mute must prevent the work, not just silence its output. A muted announcement must
   not acquire audio focus.
5. Teardown must not break the currently active route: the new route's guidance must
   work immediately after the flush (SAFEROUTE-282's requirement).
6. No behaviour change to `MapboxNavigationApp` singleton lifetime without saying so.

## Open design questions

A. Should the camera observer move to `onAttachedToWindow` (registered once, paired
   with `onDetachedFromWindow`), or stay per-route with an explicit unregister of the
   prior one? The former is simpler; confirm the observer does not depend on
   per-route state.

B. `registerNavigationCameraStateChangeObserver` — does the SDK expose a matching
   unregister, and does it require the original lambda reference? If so the current
   anonymous-lambda-per-call form cannot be unregistered at all and must be hoisted
   to a field first.

C. For Defect 3: should a muted announcement be dropped at `enqueueSpeech` (never
   synthesised), or synthesised and discarded before `play()`? Dropping is the only
   option that avoids focus acquisition. State the trade-off for a user who unmutes
   mid-route.

D. Is the 1.63 GB in scope for this ticket? Position required: the graphics figures
   are unexplained by Defects 1-3 and may be a separate map-layer defect or may be
   normal for this SDK. Do not fold an unmeasured memory claim into a teardown fix.

E. Does the per-route TTS construction happen inside the Mapbox SDK? If so, is
   releasing it within our control at all, or does it require not entering the
   fallback path (i.e. fixing item 42)?
