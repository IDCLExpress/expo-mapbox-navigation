# SAFEROUTE-288 — Protocol 1: SAFEROUTE-282 regressed speech; flush is firing per emission, not per route change

## What shipped and what it did

SAFEROUTE-282 (P1 487f71df, P2 e0a74a22, P3 a39c5bd7 PASS) replaced
`speechApi.cancel()` + `voiceInstructionsPlayer.clear()` inside `routesObserver` with
`flushSpeechForRouteChange("route change")`, plus an epoch guard that discards
synthesis whose epoch no longer matches.

Shipped as versionCode 1423130. Device measurement, R5CT81CKMHJ, 2026-09-15 04:14:

```
04:14:13.623  [SF-234] speaking: Route set. Weather checked, no rain ahead.
04:14:13.631  [SAFEROUTE-282] speech flushed (route change) ... epoch=1
04:14:13.767  [SF-197] native Mapbox navigation started
04:14:13.795  [SF-234] speaking: Route set. Weather checked, no rain ahead.
04:14:14.295  [SYNCFORGE-251] starting trip session (was STOPPED)
04:14:14.372  [SAFEROUTE-282] speech flushed (route change) ... epoch=2
04:14:14.443  [SAFEROUTE-282] speech flushed (route change) ... epoch=3
04:14:14.462  [SAFEROUTE-282] discarded stale synthesis (epoch 2 != 3)
```

Counts across the session: **13 flushes for 4 launches** (`SF-197` = 4). The flush
fires 8 ms after an announcement begins, then twice more.

Owner report: **worse than before.** Confirmed by the log — the announcement is now
reliably discarded instead of intermittently cut.

## Root cause

`routesObserver.onRoutesChanged` does NOT fire once per route change. It fires for
every routes emission: the initial set, alternatives metadata, refreshes, and cleanup.
`setNavigationRoutes()` at `onRoutesReady` produces several.

The pre-282 code called `speechApi.cancel()` + `clear()` on every one of those too, but
a cancelled `generate()` never reached `speechCallback`, so `speechInFlight` stalled —
and that stall was accidentally acting as a brake: some announcements still reached the
player. 282 removed the stall AND added an epoch guard that returns early, so the
announcement is now discarded outright. A latent defect became a deterministic one.

**The proposal author's error, recorded so reviewers can weigh it:** the design assumed
one emission per route change and never verified the observer's firing rate, which was
measurable in logs already held at the time.

## Constraint that has not changed (owner, verbatim)

> "When a user switches a new route or presses a button that completely changes the
> route ... whatever it is that was queued up to talk about on the last one has to be
> completely canceled immediately ... And then the new route he shows should be the one
> that's playing ... It shouldn't just go silent."

So: still flush on a real route change. Never flush for an emission about the route the
driver is already on.

## Candidate direction (reviewers to rule on, not a decision)

`RoutesUpdatedResult` carries a reason — `NEW_ROUTES`, `REROUTE`, `ALTERNATIVES`,
`CLEAN_UP`. Gating the flush on reason is the obvious move, but it must be verified
against the installed SDK (Mapbox Navigation v3.11.0 via
`@youssefhenna/expo-mapbox-navigation` fork `dc71895`) rather than assumed — assuming
is what produced this regression.

Open questions:

A. What are the ACTUAL reason constants and their exact import path in v3.11.0?
   Confirm against the SDK on disk, not from memory.
B. Which reasons represent a genuine route change for this purpose? Is `REROUTE`
   (driver went off-route) one where the pending announcement should survive rather
   than be dropped, since it describes the road they are on?
C. Is reason alone sufficient, or should the flush compare route IDs and act only when
   the primary route's id actually differs? An id comparison is SDK-version-independent
   and may be more robust than the enum.
D. 4 launches produced 7 `[SF-234] speaking` — still roughly two announcements per
   launch. The duplicate-announcement defect (item 72) is NOT fixed by 282 and may be
   a separate cause of overlap. In scope here or its own ticket?
E. Focus accounting is still 5 requests vs 17 abandons in this session. Does the flush
   contribute abandons without matching requests?

## Required of the implementation
1. A device log must show: exactly one flush per genuine route change, and the

2. Rollback path stated before shipping.
